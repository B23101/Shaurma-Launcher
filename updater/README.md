# shrm-updater — детальна логіка

Дивись також `../BUILD.md` для команд збірки. Тут — саме поведінка.

## Формат launcher-version.json

```json
{
  "version": "1.0.0",
  "releaseNotes": "",
  "components": [
    { "path": "launcher.exe", "sha256": "...", "size": 12345678, "url": "/launcher/launcher.exe" }
  ]
}
```

Масив компонентів (не одиничне поле) — свідомо, на випадок якщо в
майбутньому з'явиться другий незалежно оновлюваний файл. Зараз компонент
рівно один, бо весь лаунчер — один exe (embed frontend).

## Порядок дій (internal/core/core.go, Run())

1. Читає локальний `launcher-version.json` з installDir. Немає файлу →
   `Manifest{}` (порожній), не помилка — трактується як "нічого не
   встановлено".
2. GET `https://cdn.shaurma.app/launcher/launcher-version.json`.
   Немає мережі: якщо `launcher.exe` вже є на диску — запускає його як
   є (не блокує роботу через тимчасову недоступність CDN); якщо exe
   немає взагалі — повертає помилку (нічого запускати).
3. `manifest.Diff()` — порівнює SHA256+розмір кожного компонента, і
   додатково перевіряє реальний файл на диску (не лише запис у
   маніфесті) — так пошкоджений вручну `launcher.exe` теж перекачається.
4. Немає різниці → одразу запуск.
5. Є різниця → качає (ретраї×3, перевірка SHA256 кожного файлу) →
   зупиняє `launcher.exe` якщо він живий (`taskkill /IM launcher.exe /F`,
   безпечний no-op якщо вже мертвий) → `install.Apply()`.

## install.Apply — атомарна заміна (internal/install/install.go)

Windows не дає перезаписати файл запущеного процесу. Тому:
1. Видалити старий `.previous` (якщо лишився з минулого разу).
2. `rename(launcher.exe → launcher.exe.previous)`.
3. `rename(tmp/launcher.exe → launcher.exe)`.

Якщо крок 3 не вдався — крок 2 автоматично відкочується (старий файл
повертається на місце), щоб installDir ніколи не лишався БЕЗ робочого
launcher.exe. Ретраї з інтервалом 300мс, максимум 15с — покриває
випадок, коли антивірус ще тримає хендл на щойно завершеному процесі.

## Health-check після оновлення

Після встановлення нової версії — запуск і очікування 2 секунд. Якщо
процес завершився раніше (типова ознака биту білду — відсутня DLL,
пошкоджений embed) — автоматичний rollback на `.previous` і повторний
запуск старої версії, з поверненням помилки для показу в UI. Користувач
ніколи не лишається без робочого лаунчера через невдале оновлення.

## Перший запуск / чистий install-dir

Немає спеціальної гілки коду для "першого запуску" — порожній
`installDir` дає порожній локальний маніфест, `Diff()` бачить, що весь
`launcher.exe` відсутній, і качає його тим самим шляхом, що й звичайне
оновлення.

## UI (frontend/index.html)

Статичний HTML/CSS/JS (без Vite/npm-збірки), стилістика 1:1 зі старого
JavaFX `updater.css`: фон `#161616`, акцент `#ff8a00→#ffb347`, шрифти
Inter/JetBrains Mono (скопійовані у `frontend/fonts/`). Комунікація з Go
через Wails events (`updater:status`, `updater:progress`,
`updater:version`) і два біндинги (`Retry`, `CloseUpdater`).

## CLI-прапорці

- `--install-dir <path>` — override `%LOCALAPPDATA%\ShaurmLauncher`
  (корисно для тестування без зачіпання реального installDir).
- `--finalize` — прийнятий, зарезервований для майбутнього: коли
  `launcher.exe` сам ініціює оновлення і перезапускає updater, щоб
  показати інший текст у UI ("Завершуємо оновлення..." замість
  "Перевірка оновлень..."). Зараз поведінково нічого не міняє.
