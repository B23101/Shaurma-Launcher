# Підготовка та випуск Shaurma Launcher

## Поточний контракт

- Base збирається у публічному репозиторії. Повна `shaurma` — лише у приватному;
  workflow перевіряє видимість до отримання секретів і створення артефактів.
- Обидві редакції мають окремий updater із токеном лише своєї редакції.
- Компоненти підписуються перед створенням інсталятора, потім підписується setup.
  Підпис повної редакції можливий лише після погодження її приватного build origin у SignPath.
- Публічний draft Release містить контрольні суми й нотатки. Інсталятор роздається
  з офіційного сайту; Actions-артефакти Base теж публічно доступні за правилами GitHub.
  Артефакти повної редакції не можна копіювати в публічний репозиторій або реліз.
- Production-теги в shell/bootstrap/updater вимагають перевірки підпису маніфесту.
  Відсутній ключ не вимикає перевірку. SHA-256/розмір перевіряються до застосування.
  Локальні non-production збірки підтримують непідписані тестові маніфести й не є релізами.
- Усі PE мають ProductName `Shaurma Launcher` і ProductVersion `1.0.0` відповідно
  до поточного контракту SignPath. Версія релізу задається тегом і маніфестом;
  не змінюйте PE-контракт без одночасного оновлення конфігурацій підписання.

## Налаштування власника поза репозиторієм

Ці налаштування не активуються від додавання YAML/XML у git.

1. Подати заявку https://signpath.org/apply . Надати публічний код, реальний файл
   завантаження, політику підписання, учасників і докази використання проєкту.
   В одній заявці описати Base та повну редакцію й попросити погодити також приватне джерело повних збірок.
2. У SignPath створити проєкт `shaurma-launcher`, чотири конфігурації з `.signpath/README.md`,
   trusted GitHub origins та політику `release-signing` з ручним approver.
3. У GitHub створити environment `release-base` в кожному репозиторії: required reviewer,
   дозволені release-теги та контрольований workflow_dispatch. Не додавати сторонніх approver без перевірки.
4. Environment secrets: `SIGNPATH_API_TOKEN` і тільки токен відповідної редакції
   (`SHRM_BUILD_TOKEN_BASE` або `SHRM_BUILD_TOKEN_SHAURMA`). Приватній редакції за потреби
   додати Google client ID/secret. `CF_API_KEY` — лише окремий призначений для поширення
   клієнтський ключ: його можна витягти з бінарника; власний ключ задається в налаштуваннях.
   Серверні AI-ключі не вшиваються: клієнт використовує власні ключі користувача.
5. Repository variables: `SIGNPATH_ORGANIZATION_ID`, `SHAURMA_MANIFEST_PUBKEYS` (публічні
   Ed25519-ключі base64 через кому), `RELEASE_EDITION=base` у публічному та `shaurma`
   у приватному репозиторії. Перевірити, що CDN уже віддає відповідні `.sig`.
6. Увімкнути MFA для GitHub і SignPath, private vulnerability reporting, secret scanning
   та push protection, якщо доступні. Захистити main і теги v* від видалення/перезапису;
   вимагати CI та рев'ю зовнішніх PR. CODEOWNERS — лише декларація, ruleset активується окремо.
7. Публікувати на сайті й сторінці завантаження посилання з назвою `Code signing policy`,
   політику приватності, версію, SHA-256 і джерело збірки. README не має стверджувати,
   що непідписані файли вже підписані.

## Налаштовано в публічному GitHub 2026-10-30

- `main-history` забороняє видалення й force push головної гілки без винятків.
- `release-tag-history` забороняє зміну й видалення тегів `v*` без винятків.
- `main-review` вимагає одне схвалення, CODEOWNERS, вирішення обговорень і
  `ci-required` від GitHub Actions. Лише власник B23101 може обходити це правило,
  щоб Pack Manager зберіг звичайний прямий push; захист історії діє й для власника.
- `release-base` вимагає ручного підтвердження B23101, не дозволяє admin bypass
  і приймає лише гілку `main` та теги `v*`. Власник може підтверджувати свої збірки,
  оскільки другого відповідального учасника не призначено.
- `RELEASE_EDITION=base`; увімкнені secret scanning, push protection, Dependabot alerts,
  security update PR і private vulnerability reporting. Запуски з fork від зовнішніх
  авторів вимагають схвалення. Actions за замовчуванням має лише читання і не схвалює PR.

Новий `ci-required` стане доступним після публікації цього workflow Pack Manager.
До цього сторонні PR не зможуть пройти обов'язкову перевірку. Значення секретів,
ключів маніфесту, ID SignPath і Google OAuth тут не задавалися; підписаний випуск
потребує їх налаштування та погодження SignPath. MFA облікового запису потрібно перевірити власнику.

## Приватний репозиторій повних збірок

2026-10-30 створено окремий приватний репозиторій збірок із тією самою вже опублікованою
історією коду. Доступ має лише власник; `RELEASE_EDITION=shaurma`. Типові права Actions —
лише читання, автоматичне схвалення PR вимкнене, Dependabot alerts і security update PR увімкнені.
Адреса приватного репозиторію не зберігається в публічному коді.

Наявний тариф GitHub відхилив rulesets для приватного репозиторію та required reviewers
середовища. Ці механізми там **не активні**. Створено `release-base` з обмеженнями джерел
`main` і тегами `v*`, але це не замінює рев'ю та схвалення. Actions у приватному репозиторії
залишено вимкненими до погодження SignPath, налаштування секретів і перевірки політики випуску.
Ручне схвалення кожного підписання в SignPath залишається обов'язковим. Не вмикати збірки,
вважаючи недоступні GitHub protections уже налаштованими.

Pack Manager публікує зміни у звичайному порядку. Після цього власник синхронізує main
командою `scripts/sync-private-build.ps1 -Repository OWNER/PRIVATE_REPOSITORY`.
Скрипт перевіряє приватність призначення і переносить лише опублікований main без force push,
нових комітів, незакомічених локальних змін і тегів. `-WhatIf` лише перевіряє призначення.
Тег повного релізу створювати в приватному репозиторії лише після перевірки синхронізованого
коміту та завершення налаштувань підписання. Незакомічені зміни поточної підготовки ще не
потрапили в жоден віддалений репозиторій.

## Перевірки перед релізом

1. Не переписувати історію. Просканувати її з прихованими значеннями:
   `go run github.com/zricethezav/gitleaks/v8@v8.24.3 git --redact=100 --no-banner --log-opts=--all --gitleaks-ignore-path .github/gitleaks.ignore .`
   Знайдені справжні ключі відкликати у провайдера. Не публікувати звіт із самими ключами.
2. Запустити CI: тести Go-модулів, production-перевірки підписів, тест ізоляції updater,
   перевірку та збірку frontend. Виправити помилки до запиту підписання.
3. `scripts/collect-licenses.ps1` збирає повідомлення залежностей у frontend/dist/licenses
   перед пакуванням. Відсутність тексту ліцензії блокує збірку. Наявність LICENSE сама
   по собі не підтверджує сумісність: переглянути inventory та умови залежностей.
   Зберігати походження власних моделей/звуку й дозволи на сторонні логотипи та текстури.
4. Dry run: workflow_dispatch з `sign=false`. Такі файли не називати підписаними.
5. Підняти patch-версію релізу. Після звичайного push створити денний тег за AGENTS.md.
   Погодити два запити SignPath: компоненти та інсталятор. Перевірка у workflow відхиляє
   відсутні файли, невалідний підпис, іншого видавця й неправильні PE-метадані.
6. Імпортувати відповідну редакцію з Actions у приватний Pack Manager. Ця інтеграція
   не змінювалася в публічному репозиторії. Новий updater лежить у `<edition>/updater.dll`
   або `<edition>/updater.so`; імпортер має враховувати цей шлях.
7. Перевірити Authenticode/provenance; порахувати SHA-256 і розміри ПІСЛЯ підписання.
   Підписати точні байти маніфесту Ed25519 з контекстом `shaurma-launcher-manifest-v1\n`.
   Приватний ключ залишається у видавця; не завантажувати його в GitHub/репозиторій.
8. CDN: токен Base — лише читання публічного каналу, повна редакція — окремий канал.
   Наявність токена в клієнті не є авторизацією користувача. Серверний rate limit і
   доступ до приватних даних перевіряються окремо. Ці налаштування не виконуються клієнтським git.
9. Спочатку beta: чисті Windows і Linux, встановлення, оновлення, відмова при підміні
   маніфесту/підпису/компонента, деінсталяція, P2P хост і гість у приватному й публічному
   профілях, відсутність доступу без дозволу власника. Лише після цього stable і публікація.
10. Перевірити нові фінальні setup/EXE у VirusTotal; за обґрунтованого хибного визначення
    подати файл виробнику. Підписання не гарантує нуль визначень або прийняття SignPath.

## Ротація ключів маніфесту

Додати новий публічний ключ до списку зі старим, випустити й перевірити оновлення
старих клієнтів. Після достатнього охоплення перейти на підпис новим приватним ключем.
Видаляти старий публічний ключ лише після перевірки міграції підтримуваних версій;
не обмежуватися формальним числом релізів. За компрометації старого ключа потрібен
окремий план відкликання й довіреного поширення виправлення.

## Що не доводять локальні перевірки

Компіляція й тести не доводять схвалення SignPath, наявність налаштувань GitHub,
дотримання всіх сторонніх ліцензій, успішну доставку через CDN або роботу P2P між
реальними машинами. Повну готовність підтверджує підписаний beta-випуск із цими перевірками.

Власник підтвердив 2026-10-30 відкликання старого ключа з історії. .github/gitleaks.ignore містить лише точний fingerprint цього збігу; значення ключа не зберігається. Нові збіги не ігноруються.

## Спільна система скінів

Base backend збирається з тегами `production`, повний — `production,shaurma`.
`HasSkinSupport` керує гардеробом/входом окремо від `IsShaurmaEdition`; приватні модпаки
залишаються відключеними в Base. Усі інші функції спільні: акаунти, пристрої, скіни,
друзі, чат, P2P, передачі друзям, віддалений доступ до серверів і хмарний ігровий час.
На сервері перевірити доступ Base до discovery/публічних скінів і власної комірки через
користувацьку авторизацію, не відкриваючи приватні каталоги.

Для Google у дистрибутиві використовувати клієнт типу **Desktop application** з PKCE.
`SHAURMA_GOOGLE_CLIENT_KIND=desktop` у repository variables підтверджує тип;
за наявності client secret інший/відсутній тип блокує збірку. Ідентифікатор Desktop-клієнта
і його неконфіденційний client secret доступні з бінарника за дизайном OAuth public clients.
Не задавати секрет Web application або серверний ключ. В обох редакціях додати відповідний
client ID до дозволених audiences на сервісі авторизації; це зовнішнє налаштування тут не змінене.

Інсталятор дозволяє відмовитися від сервісу скінів; вибір застосовується один раз на першому
старті й не перезаписує пізніші налаштування. Дозвіл P2P — окрема опція.
Перевірити обидва варіанти на чистій Windows перед stable.

## Уточнення аудиту 2026-10-31

Foundation не допускає пропрієтарних компонентів; приватний репозиторій або
окрема конфігурація team не є винятком. До будь-якого запиту повної редакції
потрібно перевірити відкритість усіх компонентів і погодити походження з Foundation.
Конфігурація Base components: `.signpath/artifact-configuration.xml`;
інсталятор і шаблони team лишаються у `.signpath/artifact-configuration/`.

Перед публікацією вручну:
- перевірити актуальні rulesets: PR, мінімум одне схвалення, CODEOWNERS,
  скидання схвалень після нових змін, вирішення обговорень, `ci-required`;
  прямий push власника не є незалежним review;
- перевірити MFA, призначених авторів/рецензентів/схвалювачів та ручне
  схвалення кожного запиту SignPath;
- додати на домашню сторінку та сторінку завантажень опис функцій, CDN,
  перевірки маніфесту, посилання на PRIVACY.md і Code signing policy з текстом
  «Free code signing provided by SignPath.io, certificate by SignPath Foundation»;
- переглянути ліцензії залежностей та походження текстур/логотипів; окремо
  перевірити AGPL-3.0 authlib-injector і не підписувати сторонні бінарники;
- повторити redacted gitleaks по всій історії та виконати підписаний beta dry run.
  Локальний скан 2026-10-31 не запустився: Go 1.22.5 замість потрібного >=1.23,
  завантаження toolchain заблоковане мережею. Відсутність секретів не підтверджена.

Документи про внутрішню інфраструктуру `docs/vps-domain-migration-plan.md`,
`docs/dev/VPS_CLUSTER.md`, `docs/dev/P2P_HEADSCALE_SETUP.md` та
`docs/server-system/` існують локально, але не відстежуються git. Переглянути
їх перед будь-яким додаванням; приватні операційні матеріали тримати окремо.
Під час цього аудиту нічого з цих матеріалів не видалено і не додано.

## Захист завантажень за відкритими правилами Modrinth

Реалізація написана в цьому проєкті; сторонній код і сканер Modrinth не копіювалися.
Правила формату: https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack
Модерація: https://support.modrinth.com/en/articles/8793355-project-review-times

- `.mrpack`: перевірка формату, Minecraft, шляхів, дублікатів, наявності SHA-1 і
  SHA-512; обидва хеші й розмір звіряються перед публікацією файла, при пропуску
  вже завантаженого файла та завершенні Range-докачування. Початкові джерела —
  HTTPS `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com`.
  Перенаправлення також обмежені; додатково дозволені GitHub release-assets/objects CDN.
  Новий домен вимагає окремого перегляду, а не автоматичного розширення списку.
- Java: пакетний маніфест перевіряється за SHA-1 із головного маніфесту Mojang,
  кожен файл — за SHA-1 і розміром. Завантаження пишеться в окремий тимчасовий
  файл і замінює попередній лише після перевірки. Дозволені офіційні HTTPS-хости
  Mojang/Minecraft; шляхи, посилання й записи обмежені коренем Java через os.Root.
  Межі: 16 МіБ JSON, 100000 записів, 2 ГіБ на файл, 8 ГіБ на runtime-пакет.
- Підписані маніфести компонентів лаунчера, захист архівів і фільтрація команд
  у чужих бандлах зберігаються. Хеш підтверджує цілісність, а не безпечність коду мода.

Руками:
1. Перевірити живі завантаження Java 8/17/21/25 на підтримуваних ОС і імпорт
   справжніх mrpack з Modrinth/GitHub/GitLab; тести з підробленими відповідями не
   підтверджують актуальні CDN-маршрути й доступність зовнішніх сервісів.
2. Для власного каталогу організувати перевірку кожної версії модів: сканер
   шкідливого коду, ручне рев'ю підозрілих файлів, приватний канал скарг і
   процедуру відкликання небезпечних версій. Окрема серверна система не входить
   до цього публічного репозиторію; готового аналога внутрішнього сканера Modrinth тут немає.
3. Не завантажувати приватні моди на сторонні сервіси сканування без дозволу
   власника. Ні перевірений хеш, ні чистий результат сканера не є гарантією безпеки.

2026-10-31 перевірено живі Mojang-маніфести Java 8/17/21/25 та по одному малому файлу кожного runtime: SHA-1 і розміри збіглися. Повне встановлення всіх платформ цим не перевірене.
