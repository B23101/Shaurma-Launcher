## Налаштування брандмауера інсталятором

P2P потребує мережевого доступу, тому повне видалення налаштувань брандмауера
скасовано. Інсталятор використовує нативний COM API Windows Firewall замість
netsh. Обрана за замовчуванням опція P2P створює вхідне й вихідне правила
для точного шляху EXE лаунчера, для приватного та публічного профілів (маска 6).
Правила охоплюють протоколи застосунку, включно з TCP/UDP; фіксований ігровий
порт не задається, оскільки P2P використовує tsnet і динамічні порти.
Профіль домену та глобальні параметри захисту не змінюються.
Повторне встановлення оновлює власні правила; деінсталяція видаляє лише власні
правила з відповідними групою й шляхом EXE. Старі правила попередніх версій
автоматично не видаляються.

Типово setup запитує права адміністратора. Якщо користувач обрав режим без
підвищення прав, а опцію P2P залишив, інсталятор повідомляє про неможливість
налаштувати доступ. Помилки API показуються й записуються в журнал.

Якщо користувач раніше натиснув «Заборонити», відкрити `wf.msc`, знайти
вхідні блокувальні правила саме для шляху встановленого EXE лаунчера й
перевірити їх призначення. Власник комп'ютера може вимкнути помилково створені
правила блокування цього EXE, після чого повторно запустити setup як
адміністратор з опцією P2P. Не вимикати брандмауер загалом. Керовані правила
організації змінює адміністратор: локальний дозвіл їх не перевизначає.
Перевірити хост і клієнт P2P окремо у приватній і публічній мережі.

Пріоритет блокування над дозволом:
https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules

## Перевірка коду запуску та оновлень

- Bootstrap завантажує shell, замінює власний exe та перезапускається;
  shell завантажує DLL, а updater оновлює компоненти. Це легітимна, але чутлива
  до довіри поведінка.
- SHA-256 компонента перевіряється, але без вшитих публічних ключів перевірка
  підпису маніфесту вимикається. Підмінений маніфест може містити підмінені хеші.
  Windows-збірка з `-RequireSecrets` тепер вимагає ключі; кожен ключ перевіряється
  як base64 з 32 байтів. Локальна збірка без цього параметра залишається режимом
  розробки, її не слід розповсюджувати як перевірений реліз.
- Відкриття скріншота використовувало `cmd /c start`; тепер використовується
  ShellExecute. Користувацькі команди перед/після гри більше не приховують консоль.
- Інсталятор радив вимкнути Smart App Control і без доказів запевняв у безпечності.
  Тепер він радить перевірити повідомлення й передати дані для розслідування.
- Windows CI використовує звичайний Go, а не garble/UPX. Наявність необов'язкових
  garble-задач у шаблонах Wails сама по собі не означає обфускацію релізу.

Це цільова перевірка запуску, оновлень і збірки, а не повний аудит усіх підсистем
або доказ відсутності шкідливого коду.

## Порядок перевірки та випуску

1. Зберегти повний URL звіту, SHA-256, ім'я файла, джерело завантаження,
   дату сканування й версію. Не запускати підозрілий файл на робочій машині.
2. Порівняти SHA-256 із відповідним артефактом CI. Окремо перевірити setup,
   bootstrap, shell, backend.dll та updater.dll: результат одного не описує решту.
   Для локальної перевірки використовувати `Get-FileHash -Algorithm SHA256`
   та `Get-AuthenticodeSignature`. Сам підпис не доводить безпечність.
3. У налаштуваннях CI задати `SHAURMA_MANIFEST_PUBKEYS`: лише публічні Ed25519
   ключі довіреного видавця. Приватний ключ залишається поза репозиторієм.
   Видавець має публікувати відповідний `.sig` над точними байтами маніфесту
   з контекстом `shaurma-launcher-manifest-v1\n`. Не створювати новий ключ навмання:
   він має відповідати ключу видавця. Відсутній/невалідний підпис мусить блокувати оновлення.
4. Зібрати реліз із чистого checkout через CI, підписати всі PE-компоненти
   та інсталятор. Перевірити, що CDN роздає саме ці підписані байти і що хеші
   в підписаному маніфесті пораховані після Authenticode-підписання.
5. У відокремленій тестовій Windows із увімкненим захистом перевірити встановлення,
   оновлення, відмову при зміненому маніфесті/підписі/компоненті та відкриття
   скріншотів зі шляхами з пробілами й символом `&`. Не вимикати захист і не
   додавати винятки для проходження перевірки.
6. Після перевірки походження й поведінки подати конкретний файл, який вважається
   помилково визначеним, до виробників антивірусів. Для Microsoft обрати
   Software developer на https://www.microsoft.com/en-us/wdsi/filesubmission .
   Додати SHA-256, версію, посилання на джерела/CI, підпис і опис оновлювача.
   Дочекатися висновку; не називати спрацювання хибним лише через відкритий код.
7. Повторно перевірити фінальні підписані файли й зберегти результати.
   Нові байти потребують нової перевірки. Для випуску змін підняти patch-версію;
   не змінювати фіксовані PE/SignPath-версії без узгодження конфігурації підписання.

Microsoft про розгляд спрацювань і послідовне підписання:
https://learn.microsoft.com/en-us/defender-xdr/developer-faq
